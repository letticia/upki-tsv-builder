# UPKI申請TSVビルダー

UPKI電子証明書発行サービス（NII）の申請TSVファイルを、利用管理者との対話で安全に作成するためのスキル。

**想定利用者は大学・研究機関の利用管理者で、PKIの専門家とは限らない。** 専門用語（CSR、DN、シリアル番号、ACMEアカウントIDなど）は初出時に1〜2文で平易に説明しながら進めること。

## 全体ワークフロー

1. **申請種別の特定** — どの証明書のどの手続きかを確認する
2. **項目の聞き取り** — 該当するreferencesファイルを読み、必須項目から順に質問する
3. **入力の検証** — 聞き取りながら形式チェック。最終的にスクリプトで機械検証する
4. **プレビューと確認** — 生成内容を表形式で見せ、ユーザーの承認を得る
5. **TSVファイル生成** — `scripts/build_tsv.py` で生成（Shift-JIS / CR+LF / タブ埋めはスクリプトが保証）

## ステップ1: 申請種別の特定

まず以下の2段階で特定する。ユーザーの発言から明らかな場合は確認だけして進む。

**FQDNやURLだけが提示された場合（例:「www.example.ac.jpの証明書を更新したい」）は、先に「FQDN起点フロー」（後述）で現在の証明書情報を取得すると、種別の判断も項目の事前入力もできる。**

**証明書の種類:**
- 従来方式のサーバ証明書（TSVで都度申請し、証明書を手動でインストールする方式）
- ACME（証明書の取得・更新を自動化する方式。UPKIではACME利用開始にもTSV申請が必要）

**手続きの種類:**

| 種別ID | 手続き | 主な利用場面 | 参照ファイル |
|---|---|---|---|
| `server-issue` | サーバ証明書 発行申請 | 新規にサーバ証明書が必要 / DNを変更したい | references/server-issue.md |
| `server-renew` | サーバ証明書 更新申請 | 有効期限が近い・切れた証明書の継続利用、失効済み証明書の再発行 | references/server-renew.md |
| `server-revoke` | サーバ証明書 失効申請 | 証明書が不要になった / 秘密鍵が漏洩した | references/server-revoke.md |
| `acme-create` | ACME利用情報 作成申請 | これからACMEで証明書を自動発行したい | references/acme-create.md |
| `acme-renew` | ACME利用情報 更新申請 | 既存ACMEアカウントの登録内容（dNSName等）を変更したい | references/acme-renew.md |
| `acme-suspend` | ACME利用 停止申請 | ACMEの利用をやめる | references/acme-suspend.md |
| `acme-revoke` | ACME発行証明書 失効申請 | ACMEで発行済みの証明書を失効したい | references/acme-revoke.md |

迷いやすいポイント:
- 「証明書の更新」でも、ACMEで発行した証明書なら通常はACMEクライアントが自動更新するためTSVは不要。ユーザーがACME利用中で「更新申請」と言った場合は、何を変更したいのかを確認する（登録情報の変更なら `acme-renew`）。
- 従来方式で**同一DNのまま更新する場合は、必ず更新申請（`server-renew`）**を使う（新規発行ではない）。
- **更新に伴う旧証明書の失効TSVは、UPKIシステム側で自動生成され、必要な場合に登録担当者へ送付される。利用管理者が作成する必要はない。** ユーザーが「更新したので旧証明書の失効TSVを作りたい」と言った場合は、作成不要であること、置き換え完了を登録担当者へ通知すればよいことを案内する（`server-revoke` は証明書が不要になった場合や鍵漏洩時など、能動的な失効のためのもの）。
- DN（主体者DN）を変更する場合、サーバ証明書では「更新」ではなく「新規発行」になる。
- 旧来方式からACMEへの移行は `acme-create`（移行後の旧証明書の扱いは登録担当者へ確認）。

種別が決まったら、**対応するreferencesファイルを必ず読んでから**聞き取りを始める。項目仕様を記憶で補わないこと。

## FQDN起点フロー（URLやFQDNから始める場合）

ユーザーがサーバのURL/FQDNを示して「更新したい」「移行したい」「証明書をなんとかしたい」と言った場合のフロー。

### 1. 現在の証明書情報を取得

```bash
python3 scripts/inspect_server.py --host www.example.ac.jp
```

- 失敗した場合・「プロキシが差し替えた証明書」と警告された場合は、**直接接続の結果を絶対に使わず**、スクリプトが提示する `openssl s_client` コマンドをユーザーの端末で実行してもらい、出力を貼り付けてもらって `--pem` モードで解析する。ブラウザから証明書をエクスポートしたPEMでもよい。
- 出力JSONには `server_renew_prefill` / `acme_create_prefill` / `server_revoke_prefill` が含まれ、build_tsv.py の records にほぼそのまま使える。

### 2. 結果の提示と方式の提案

取得した情報（DN・有効期限・残り日数・鍵種・SANs・発行者）を分かりやすく示したうえで、**次の更新方法として2つの選択肢を提示する。ACME移行を第一の推奨として紹介しつつ、選択は必ずユーザーに委ねる**こと。

提案の例（トーンの参考）:

> 次の更新には2つの方法があります。
>
> **おすすめ: ACMEへの移行** — 今回TSVを1回申請すれば、以後の証明書の発行・更新はサーバ上のACMEクライアント（certbot、legoなど）が自動で行うようになり、毎年のCSR作成・TSV申請・手動インストールが不要になります。サーバ証明書の有効期間は業界全体で短縮が続いており、手動更新の負担は今後さらに増えるため、NIIもACMEへの移行を推奨しています。サーバにACMEクライアントを導入する初期作業が必要です。
>
> **従来方式での更新** — 今まで通りCSRを作成してTSVで更新申請します。サーバ側の構成変更は不要ですが、次回以降も同じ手動作業が必要です。
>
> どちらで進めますか？サーバの運用状況（クライアント導入の可否など）が分からなければ、それを伺ってから一緒に判断することもできます。

注意:
- ユーザーが従来方式を選んだら、それ以上ACMEを推さずに気持ちよく `server-renew` フローへ進む。
- 発行者がUPKI（NII Open Domain CA）でない証明書だった場合は、UPKI管理外の可能性をユーザーに確認する。
- 期限切れ・残り日数僅少の場合はその旨を伝え、手続きを急ぐ必要性を共有する。

### 3. 事前入力して該当フローへ

- **ACME移行を選択** → `acme-create` フローへ。prefillのDN・FQDN・SANs・プロファイルIDを提示して確認してもらう。加えて:
  - 現行証明書のDNにOUが含まれる場合、ACMEではOUを使えないため除外したDNになることを説明する。
  - **既存の同一主体者DNのレコード（従来方式の証明書）があってもACME作成申請はそのまま受理される**（自動更新での事故を防ぐための仕様）。事前の失効は不要。
  - **旧証明書（従来方式）の失効は必須ではない。** ACMEで発行した新証明書への置き換えと動作確認が完了した後、**失効したい場合のみ** prefillの `server_revoke_prefill` から失効TSV（理由は通常 4: superseded）を生成する。移行直後は切り戻し（旧証明書に戻す）が必要になる可能性もあるため、**旧証明書を残したまま有効期間満了を待っても問題ない**ことを利用管理者に伝える。
  - 移行作業全体の流れ（TSV申請 → ACMEアカウント情報の受領 → クライアント設定 → 発行確認 → 旧証明書の置き換え・動作確認 → 希望する場合のみ旧証明書の失効申請）も簡単に示すと親切。
- **従来方式の更新を選択** → `server-renew` フローへ。prefillのDN・シリアル番号・FQDN・SANsを提示して確認してもらう。CSR（新しい鍵ペアで作成）は別途必要。**旧証明書の失効TSVはシステム側で自動生成されるため、利用管理者が作成するのは更新申請TSVのみ**（置き換え完了後に登録担当者へ通知するだけでよい）。
- いずれの場合も、**prefill値は必ずユーザーに見せて承認を得てから使う**。特にDNのST/Lが機関の届出値と一致しているかは本人にしか分からない。



## ステップ2: 項目の聞き取り

referencesの項目表に従い、以下の方針で進める。

- **1回の質問は1〜3項目まで。** 関連する項目はまとめてよい（例: 利用管理者の氏名・所属・メール）。
- **必須項目（○）→ 条件付き・任意項目（△）の順。** 任意項目は「空欄でも構いません」と添える。
- **専門用語は説明してから聞く。** 例:
  - CSR: 「証明書の元になる申請データで、サーバ上で秘密鍵と一緒に作成するテキストファイルです。`-----BEGIN CERTIFICATE REQUEST-----` で始まる内容をそのまま貼り付けてください」
  - シリアル番号: 「証明書ごとに割り当てられた識別番号です。発行時の通知メールや、ブラウザの証明書表示画面で確認できます」
- **複数件の申請に対応する。** 1ファイルに最大99件まで。複数件ある場合は、共通項目（利用管理者情報など）を先に確認し、件ごとに異なる項目だけを順に聞くと効率がよい。表形式（Excel貼り付け等）でまとめて受け取ってもよい。

### 聞き取り時の注意（仕様上の重要ポイント）

- **ST / L は機関ごとに固定値。** サービス窓口に届け出た都道府県・市区町村のローマ字表記しか使えない。ユーザーが不明な場合は「UPKI証明書 主体者DNにおける ST および L の値一覧」（https://meatwiki.nii.ac.jp/confluence/pages/viewpage.action?pageId=59022761）か機関の登録担当者に確認するよう案内する。
- **失効理由でコード1（KeyCompromise）は、秘密鍵が第三者に漏洩した（恐れがある）場合以外は絶対に選ばせない。** 通常の更新に伴う失効は「4: superseded」。ユーザーが1を選ぼうとしたら、本当に鍵の漏洩事案かを必ず確認する。
- **ACMEのDNにはOUが使えない**。また属性名は大文字のみ、「=」や「,」の前後にスペース不可。
- 利用管理者mailは証明書取得URL等の通知先になるため、確実に受信できるアドレスかを念押しする。

## ステップ3〜5: 検証・プレビュー・生成

聞き取りが終わったら、レコードをJSONにまとめて検証スクリプトを実行する。

```bash
# 入力JSONを作成（形式はスクリプト冒頭のdocstring参照）
python3 scripts/build_tsv.py input.json -o 申請ファイル.tsv
```

スクリプトが行うこと:
- 全項目の形式検証（文字種・文字数・DN順序・メール形式・シリアル番号形式など）
- CSRの解析と検証（鍵種・鍵長、CSR内DNと項目1のDNの一致、プロファイルIDとの整合）
- Shift-JISで表現できない文字（JIS第一・第二水準外）の検出
- 件数上限（99件）チェック
- 正しい列数のタブ埋め、Shift-JISエンコード、CR+LF改行での出力

**エラーが出たら、エラーメッセージを初心者向けに翻訳してユーザーに伝え、該当項目だけ聞き直す。** 警告（warning）は内容を伝えたうえで、ユーザーが了承すれば続行してよい。

生成前に必ず、全項目を日本語の項目名つきの表でプレビューし、ユーザーの承認を得ること。CSRは長いので先頭・末尾の数十文字だけ示せばよい。

生成後はファイルを提示し、あわせて次のステップを案内する:
- 作成したTSVは**各機関で決められた手続きに従い、登録担当者へ送付**する（本システムに直接アップロードするのは登録担当者）
- ファイルはShift-JISのため、エディタで開き直して保存し直すと文字コードが変わる恐れがあることを注意する

## してはいけないこと

- referencesを読まずに記憶だけで項目仕様を答える・TSVを手書きする
- スクリプトを通さずにTSVファイルを直接出力する（エンコード・タブ数の保証ができない）
- ユーザーが指定していない値を勝手に補完する（特にDN、シリアル番号、失効理由）
- 秘密鍵の内容を聞き出す・受け取る。CSR作成の相談には応じてよいが、秘密鍵そのものは絶対に扱わない。誤って貼り付けられた場合は、その鍵は漏洩したものとして作り直すよう助言する
